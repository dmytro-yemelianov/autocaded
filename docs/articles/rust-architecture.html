AutoCADED: a native CAD editor built for exact files and boring failures

AutoCADED is a handwritten Rust editor that reads, edits and writes classic DWG (AC1.2 and AC1.40) and historical DXF drawings. This article describes how it is put together, and the handful of design rules that make it fast, compatible and very hard to make lose data.

The shape of the system

The workspace is six crates arranged as a strict hourglass. A dependency-free model sits in the middle. Codecs, the editor and the renderer each depend only on that model and never on each other. One application crate at the top is the only place that touches files, windows, sockets or clocks.

A model that says exactly what the file says

A drawing is a header plus a flat, ordered list of items. Order is content: block definitions, loose geometry and font selections interleave, and the order in which they appear changes what renders. So the model never reorders anything.

  • Items are an entity, an erased entity, a block definition, or a rectangular repeat group.
  • Entities are geometry (line, circle, arc, text, insert, trace, solid, point, shape), plus three wrappers: OnLayer keeps layer orthogonal to geometry, Erased marks an erased member inside a live group, and Load switches the active font or shape library in document order.
  • The header carries limits, view, snap/grid/axis modes, units, layer colours, a separate set of OFF layers, and the drawing-scoped FILLET radius. Unrecognised header bytes ride along untouched, but are excluded from equality, so they never make a drawing look "changed".

Erasure is data, not deletion. An erased record stays in the model and in the saved DWG, which is what makes OOPS and faithful round-tripping possible. Visibility is a pure function over the header: hiding a layer hides geometry, but font selections still run, so turning a layer off never changes how other text renders.

Codecs that refuse rather than guess

Both codecs work on byte slices and return byte vectors. They never open a file, so the same code serves the GUI, the headless server and the tests.

Reading DWG

  1. Check the declared record count (≤ 65,535) and end offset against the real file length before walking anything.
  2. Walk records one at a time, checking every step against the record limit and the end offset.
  3. Assemble groups with a depth cap of 64; blocks and repeats must nest properly.
  4. Finish only if the walk lands exactly on the declared end and the count matches.

Writing DWG and DXF

  1. Validate the whole drawing before allocating output.
  2. Refuse anything the target format cannot store faithfully: a nonzero FILLET radius in AC1.2 or DXF, non-Latin-1 text, out-of-range layers, ambiguous erasure history.
  3. Use checked arithmetic for every size and offset.
  4. Return a typed error with a user-facing message; the session keeps the old file and the unsaved document.

The rule is simple: a save either writes a file that reopens to the same drawing, or it writes nothing and says why. Nineteen typed DWG error variants and nine shared group errors exist so that "why" is always specific.

Round-trip guarantees are tested, not assumed. DWG output re-encodes to identical bytes, a reference DXF sample round-trips byte for byte, and every bundled sample drawing reopens to the same structure after a save.

An editor with no side effects

The editor is a state machine with one state per prompt (136 of them). Commands are dispatched from a single match on the command name and its aliases. Crucially, the editor never performs I/O. When a command needs the outside world, it returns an Effect value instead: save this drawing, write this block, load this menu, start this script, wait this long. The session decides how to carry it out.

That separation buys three things:

  • Determinism. Every editor test is a pure function of inputs. No temp files, no sleeps, no flakiness.
  • Staging. Multi-prompt operations stage their result and commit once. External INSERT reads and validates the whole source file at the first prompt, holds it, and only commits at the last prompt as a single UNDO step. Cancel at any point leaves nothing behind.
  • One undo model. Each committed change pushes a full snapshot of the drawing plus editor history. UNDO pops one. Failed or cancelled commands are tested to leave the undo stack exactly as it was.

Selection

Every feature that asks "which objects?" uses one traversal: typed IDs, ALL and LAST, mouse picks, window selection, HATCH boundaries, highlighting and the API's object count. IDs are 1-based in drawing order over live top-level owners, so a repeat group or an inserted block is one object. Hidden geometry can't be picked, and turning a layer off never renumbers anything else.

What makes it fast

Speed here mostly comes from not doing work, and from knowing up front how much work is allowed.

Budgets everywhere, charged before the work

Every traversal that a hostile or merely huge drawing could blow up has an explicit limit, and the cost is charged before the work runs. Running out of budget is a clean, atomic refusal, never a hang or a half-finished edit.

An indexed hatch sweep

Hatching sweeps parallel lines across a boundary. The straightforward version tests every boundary edge against every line, which is fine for a rectangle and terrible for a boundary made of thousands of islands. The sweep now keeps boundary pieces sorted by where they start and end across the sweep direction, plus an active set, so each line only examines pieces it can actually cross. Arcs are split at their extremes so every piece is monotone, and every piece uses the same half-open crossing rule, which makes vertex and tangent rows unambiguous.

Rendering

Rendering is two pure stages: flatten the drawing into polylines and filled polygons, then rasterise with tiny-skia into a software buffer. Flattening returns diagnostics alongside geometry, so bad font data or an exhausted budget is reported instead of silently drawing something wrong. A saved view that can't be shown on the current canvas falls back to fitting the limits, for display only, so a damaged file still opens to a usable window.

What makes it fail-proof

One owner for everything stateful

A single Session owns the editor, the open document, fonts, the menu, the input line, any running script and any paused menu macro. The GUI, the Unix-socket API and the MCP server all call the same typed operations on it. There is one code path to get right, and every automation test exercises the same logic a person clicking in the window does.

Saves that can't destroy your file

  1. Resolve the destination, following symlinks; refuse non-regular, read-only or OS-locked files before writing a byte.
  2. Write the new drawing to a private temp file beside the destination (created owner-only when replacing), and flush it to disk.
  3. If the destination exists, copy its current bytes to a second temp file, flush, and rename it over NAME.BAK.
  4. Rename the new file over the destination, then flush the directory.

The destination is never missing or truncated at any step, an older backup is only replaced by a complete one, and a failure anywhere leaves the document attached and still marked unsaved. Leftover temp files are removed on every error path. If only the final directory flush fails, the save counts as done with a warning, because retrying would otherwise back up the new file over the real previous version.

Reading user-named files

External drawings, scripts, menus and hatch pattern files all go through one reader. It accepts only regular files, so a folder, pipe or device can neither hang the program nor shadow a real file further down the search path. It checks the size against a per-kind cap before reading and reads at most one byte past the cap, so a file that grows mid-read is still refused.

Never blocking the window

Command scripts run on the event loop, not on a thread that sleeps. DELAY records a deadline on an injectable clock. The window's idle hook runs due script items, then waits exactly until the next deadline. Any real user input interrupts a running script before it is handled, and RESUME continues at the exact next unread byte. Tests drive all of it with a fake clock, so timing behaviour is deterministic.

Atomic commands

FILLET computes its geometry before touching either line. HATCH charges its whole budget before emitting a stroke. BREAK, ARRAY and CHANGE stage their full result before one commit. Each of these has tests asserting that a refused or cancelled command leaves the drawing, the undo stack and the unsaved flag exactly as they were.

What makes it compatible

Compatibility is treated as evidence, kept in four separate classes that every behaviour document labels explicitly:

  • Reference files. Drawings saved by the reference program are compared against the editor's output at a geometry tolerance of 10-10, with ordering and every field checked.
  • Black-box behaviour tests. Scripted sessions run the reference program and compare the drawings it saves with what the Rust editor produces from the same input. Every claim about reference behaviour in the docs must be backed by one of these tests, and the test must be one that would fail if the claim were false.
  • Help text. Where no behavioural run exists, the documented command help defines the contract.
  • Native policy. Where the editor deliberately differs (retrying instead of abandoning a command, millisecond DELAY units, safer saves), the docs say so plainly.

A per-command matrix tracks all 57 command names with what is implemented, what is not, and which kind of evidence backs it. The bundled sample drawings are round-tripped on every full test run: the first backup must match the original byte for byte, and the reopened drawing must match structurally with numeric drift of at most four units in the last place.

Sample drawings are not kept in git. Tests that need them say so loudly when they are absent, and fail outright when AUTOCAD_REQUIRE_CORPUS=1 is set, so a green run can never quietly mean "skipped".

Every feature also went through an independent review as an exact patch before integration, by a reviewer who had not written it and who built counterexamples rather than reading for style. That process caught a hatch row that vanished at certain vertices, a pattern file that could freeze the window for minutes, a save path that could leave an undeletable temp file on a locked drawing, and a CI configuration that had never actually compiled on a clean machine.

Automation built in

The same session is reachable three ways: the native window, an owner-only Unix socket attached to a running window, and an MCP server over stdio that can run headless or attach to that socket. The MCP server exposes 17 tools (new, open, command, point, click, motion, state, drawing, save, cancel, report, frame, quit, and four script controls), each with a strict input schema, and returns frames as PNG or raw RGBA. This is what lets an agent, a test or a person drive exactly the same editor.
